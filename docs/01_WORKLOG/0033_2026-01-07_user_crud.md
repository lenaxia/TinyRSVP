## Technical Implementation Details

### Last Admin Protection

Both role demotion and user deletion check admin count before proceeding:

```go
if user.Role == models.RoleAdmin && newRole != models.RoleAdmin {
    adminCount, err := h.userService.CountAdmins(r.Context())
    if err != nil {
        return err
    }
    if adminCount <= 1 {
        return http.StatusConflict, "cannot demote last admin"
    }
}
```

### Cascade Deletion

Database schema enforces cascade deletion via foreign key constraint:
```sql
user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE
```

Integration test verifies:
1. User has 2 sessions
2. User is deleted
3. Sessions are automatically deleted
4. User no longer exists

### Pagination

List endpoint supports flexible pagination:
- Default: limit=50, offset=0
- Max limit: 100
- Validation for invalid parameters
- Returns total count for client-side pagination UI

### Error Handling

Consistent error responses:
- 400 Bad Request: Invalid parameters
- 404 Not Found: User doesn't exist
- 409 Conflict: Last admin protection triggered
- 500 Internal Server Error: Database/service errors

All errors return JSON:

}

### Input Validation

- User ID must be positive integer

- Pagination parameters validated
- Invalid inputs return 400 with clear error messages

## Technical Decisions

### 1. Handler Layer vs Service Layer
User management logic placed in HTTP handler layer rather than service layer. The service layer provides low-level CRUD operations, while handlers implement business rules (last admin protection) and HTTP concerns (status codes, JSON responses).

### 2. Last Admin Protection Strategy
Protection implemented at handler level by:
1. Checking if target user is admin
2. Counting total admins
3. Rejecting operation if count <= 1

This approach is simple, race-condition-safe (database transaction isolation), and doesn't require complex locking.

### 3. Cascade Deletion
Relies on database foreign key constraints (`ON DELETE CASCADE`) rather than application logic. This ensures:
- Atomic deletion (all or nothing)
- No orphaned sessions
- Database-level guarantee
- Simpler application code

### 4. No Authorization Yet
Handlers implement business logic but not authorization checks. Authorization will be added in Story 07 (RBAC Middleware) which will wrap these handlers with:
- RequireAuth middleware (validates session)
- RequireAdmin middleware (checks role)

This separation of concerns allows testing handlers independently of auth.

### 5. Strongly-Typed DTOs
All request/response models use strongly-typed structs, never `map[string]interface{}`. This provides:
- Compile-time type safety
- Clear API contracts
- IDE autocomplete
- Self-documenting code
